- **"룰 기반과 비교"** — 학습이 단순히 "되는가"가 아니라 "실무 표준보다 나은가"를 검증한다는 평가 철학.

# 슬라이드 3 — 프로젝트 개요 / 과제 요구사항 대응

## 화면 내용
프로젝트 목표 한 문단 + 과제 요구사항 4항목과 본 프로젝트 적용을 짝지은 표.

| 과제 요구사항 | 본 프로젝트 적용 |
|---|---|
| RL 모델(DQN/AC/PPO/SAC 등, 여러 개 비교 가능) | Double DQN + PPO 2종 직접 구현, 룰·고정 포함 4개 정책 비교 (SAC·연속제어는 향후) |
| 딥러닝 라이브러리(DeZero/PyTorch/TF) | 교재 DeZero 사용 — MLP·옵티마이저만 라이브러리, 알고리즘 로직은 전부 직접 구현 |
| 시뮬레이터·데이터셋(OpenAI Gym 등) | Gymnasium 표준 인터페이스(reset/step)의 자체 큐잉 시뮬레이터 직접 구현 |
| 제출물(PPT + 소스) | 발표자료 + autoscaling-rl/ 전체 소스 (README 포함) |

## 배경/원리
- **"2종 직접 구현"의 의미**: DQN과 PPO는 학습 패러다임이 정반대입니다. DQN은 가치를 추정해 간접적으로 정책을 얻는 off-policy 방식이고, PPO는 정책을 직접 최적화하는 on-policy 방식입니다. 두 계열을 모두 구현한 것은 "한 알고리즘이 우연히 잘된 것"이 아니라 문제 자체의 성질을 다각도로 검증했다는 뜻입니다.
- **DeZero를 쓴 의미**: DeZero는 교재 『밑바닥부터 시작하는 딥러닝 3』의 교육용 자동미분 프레임워크입니다. PyTorch처럼 DQN/PPO 손실함수가 내장돼 있지 않습니다. 즉 Experience Replay, Target Network, Double DQN 타깃 계산, GAE, Clipped surrogate를 **전부 손으로 짜야 합니다**. 이게 "알고리즘을 이해했다"는 가장 강력한 증거입니다. 실제로 `agents/common.py`에는 DeZero에 없는 gradient clipping을 직접 구현한 `clip_grads`가 있습니다.
- **Gymnasium 표준**: `reset()`/`step()` 인터페이스를 따르므로, 나중에 Stable-Baselines3 같은 검증된 라이브러리로 갈아끼워 "내 구현이 맞는지" 교차검증할 수 있습니다.

## 시사점
이 표 한 장이 "과제를 형식적으로 끝낸 게 아니라, 요구된 자유도(여러 모델 비교, 자체 시뮬레이터)를 적극 활용했다"는 인상을 줍니다. 특히 **밑바닥 구현 + 4개 정책 비교**는 난이도와 성실성을 동시에 어필하는 포인트입니다.

## 예상 질문
- *"왜 SAC는 안 했나?"* → 행동이 ±4/유지의 3개 이산 행동이라 연속 제어용 SAC는 부적합. 행동을 연속(가변 폭 조절)으로 바꾸는 향후 과제로 분리.
- *"PyTorch가 더 쉬운데 왜 DeZero?"* → 과제 권장 라이브러리이자, 알고리즘을 블랙박스로 쓰지 않고 내부 동작을 코드로 이해·검증하기 위해서.

# 슬라이드 4 — 적용 문제 ①: 자원은 '항상' 어긋난다

## 화면 내용
MSA 트래픽은 하루 주기로 출렁이고(오전/저녁 피크) 예고 없는 버스트가 발생하는데, worker thread pool은 한 번 튜닝한 고정값. 부족하면 큐 대기 → SLA 위반, 과잉이면 메모리·컨텍스트 스위칭 낭비. 하단 3박스(지연↑ / 비용↑ / 최적점 이동).

## 배경/원리
- **트래픽의 이중 구조**: 실제 코드(`envs/traffic.py`)의 `make_traffic()`는 두 성분을 합성합니다. ① 가우시안 두 개로 만든 **일일 사이클**(오전 피크는 0.55π 위치, 저녁 피크는 1.35π 위치, 진폭·위상은 매 에피소드 랜덤), ② **버스트**(에피소드당 1~3회, 각 5~15 step, +50~150% 급증), 그리고 ③ 4% 관측 노이즈. 즉 "예측 가능한 주기"와 "예측 불가능한 스파이크"가 공존합니다.
- **고정값의 딜레마**: 피크에 맞춰 크게 잡으면 평상시 90%의 시간 동안 자원이 놀고, 평상시에 맞춰 작게 잡으면 피크마다 무너집니다. 어느 한 고정값도 24시간을 만족시키지 못합니다.
- **두 비용의 비대칭**: 자원 부족의 비용(SLA 위반 → 사용자 이탈)은 자원 과잉의 비용(메모리·CS 낭비)보다 훨씬 치명적입니다. 이 비대칭이 뒤(보상 설계)에서 "SLA 위반 가중치 1.0 vs 비용 가중치 0.30"으로 정량화됩니다.

## 시사점
"자원량을 정적으로 정하는 것 자체가 틀린 접근"이라는 문제의식. 정답은 특정 숫자가 아니라 **트래픽에 반응하는 정책(함수)**라는 프레임 전환을 청중에게 심는 슬라이드입니다.

## 예상 질문
- *"그냥 모니터링 보고 사람이 조절하면 안 되나?"* → 버스트는 분 단위로 발생하고 예고가 없어 수동 대응이 불가능. 자동 정책이 필요.

# 슬라이드 5 — 적용 문제 ②: 두 비용은 '단순 트레이드오프'가 아니다  ★핵심

## 화면 내용
트레이드오프 정의(하나를 좋게 하면 다른 하나가 나빠지는 교환)와, 이 문제에서는 그 교환이 깨진다는 설명. 그래프의 빨간 구간 = 비용과 지연이 함께 나빠지는 구간. ① 비단조 용량(c*를 넘으면 증설할수록 비용↑·지연↑), ② 곡선이 c*에서 접혀 되돌아 올라감. c*와 교환 구간이 트래픽 λ에 따라 이동.

## 배경/원리
이 슬라이드가 **프로젝트 전체의 지적 핵심**입니다. 논리를 단계별로 풀면:

1. **단순 트레이드오프라면 RL이 불필요**: 만약 "스레드↑ = 지연↓ & 비용↑"이 단조롭게 성립한다면, 비용과 지연에 가중치를 매겨 미분=0인 균형점 하나만 찾으면 끝납니다. 이건 정적 최적화 문제이지 강화학습 문제가 아닙니다.

2. **그러나 용량이 비단조**: 실제 코드의 용량 함수는
   ```
   capacity(c) = c·μ / (1 + α·max(0, c−knee)²/knee²)
   ```
   `knee`(=32)까지는 분자 `c·μ`가 지배해 용량이 증가하지만, 그 이상에서는 분모의 오버헤드 항이 제곱으로 커져 **용량이 오히려 감소**합니다(μ=25, α=2 기준 c≈39에서 정점). 즉 스레드를 더 넣으면 컨텍스트 스위칭·CPU 경합으로 처리량이 떨어집니다.

3. **그래서 "둘 다 손해" 구간 발생**: c*를 넘어 증설하면 비용은 당연히 오르고(스레드↑), 용량이 줄어 지연도 오릅니다. 교환이 아니라 양쪽 다 나빠지는 구간이 생깁니다 — 이게 그래프의 빨간 구간.

4. **최적점이 움직인다**: 적정 c*는 현재 트래픽 λ에 의존합니다. λ가 크면 더 많은 스레드가 필요하지만 knee 한계가 있어 무한정 못 늘립니다. λ가 작으면 c*도 작아집니다. 즉 **단일 최적점이 아니라 λ에 따라 이동하는 곡선**을 추적해야 합니다.

## 시사점
"왜 하필 강화학습인가"에 대한 가장 설득력 있는 답입니다. 정적 최적화나 단순 룰로 충분했다면 RL은 과잉 설계입니다. 비단조성과 최적점 이동이 RL을 **정당화**합니다. 발표에서 여기를 흐리면 "굳이 RL?"이라는 근본 의문이 남습니다.

## 예상 질문
- *"비단조 용량이 실제로 존재하나, 인위적 설정 아닌가?"* → 스레드 과다 시 컨텍스트 스위칭 비용 증가는 OS 스케줄링의 실측 현상. knee·α 값은 가정이지만 현상 자체는 실재. 11번 슬라이드의 실측 곡선(c≈39 정점) 참조.

# 슬라이드 6 — 적용 문제 ③: 왜 강화학습인가

## 화면 내용
4가지 근거(순차적 의사결정, 지연된 보상, 움직이는 최적점, 보상함수로 운영목표 표현)와 우측의 "문제 ↔ MDP 대응" 박스.

## 배경/원리
- **순차적 의사결정 + MDP 구조**: 현재 스레드 조절(`step`에서 `self.c` 변경)이 미래 상태에 영향을 줍니다. 핵심 매개는 `backlog`입니다. 코드에서 `self.backlog = max(0, self.backlog + (lam − cap))` — 지금 용량이 부족하면 처리 못 한 요청이 backlog로 누적되고, 다음 step의 지연(`w += backlog/cap`)을 키웁니다. 즉 "지금의 결정 → 미래의 상태 → 미래의 보상"이라는 마르코프 연쇄가 성립합니다.
- **지연된 보상**: backlog가 쌓이면 한 step에 해소되지 않고 여러 step에 걸쳐 지연을 유발합니다. 따라서 피크가 오기 **전에** 미리 증설하는 선제 행동이, 당장은 비용을 쓰지만 미래의 큰 SLA 페널티를 막아 누적 보상에서 이득입니다. 이런 "지금 손해, 나중에 이득" 구조는 미래 보상을 할인 합산하는 RL이 자연스럽게 다룹니다(γ=0.99).
- **보상함수로 운영목표 표현**: `w_sla`, `w_cost`, `w_under`, `w_thrash` 가중치를 바꾸면 "공격적으로 증설하는 정책"부터 "비용에 민감한 보수적 정책"까지 성격을 설계할 수 있습니다. 운영 정책의 철학을 코드 한 줄로 조정 가능.

우측 MDP 대응: 환경=MSA 큐잉 모델, 상태=트래픽·이용률·지연·자원량, 행동=−4/유지/+4, 보상=−SLA위반−초과증설비용, 정책=동적 튜너.

## 시사점
5번이 "정적 방법으로 안 되는 이유"라면, 6번은 "RL이 잘 맞는 이유"입니다. 두 슬라이드가 함께 RL 선택을 양면으로 정당화합니다.

# 슬라이드 7 — 적용 문제 ④: 인스턴스 고정 환경의 유일한 동적 자원

## 화면 내용
인스턴스(JVM 프로세스) 수 고정 제약 → 수평 확장 불가 → 인스턴스 오토스케일링 불가. 조절 가능한 자원 = Undertow worker thread pool. IO thread(조절 대상 아님) vs worker thread(조절 대상) 구분. 런타임 조정 가능(`ThreadPoolExecutor.setCorePoolSize`).

## 배경/원리
- **Undertow 스레드 모델**: Undertow(Spring Boot의 내장 WAS 옵션)는 두 종류의 스레드를 씁니다. **IO thread**는 논블로킹 방식으로 네트워크 연결 수락·송수신만 담당하며 보통 CPU 코어 수로 고정합니다(조절해도 의미 없음). **worker thread**는 실제 비즈니스 로직(컨트롤러, DB 조회, 외부 API 호출 등 블로킹 작업)을 처리합니다. 트래픽 처리량을 좌우하는 건 worker thread입니다.
- **왜 이것만 조절 가능한가**: 인스턴스 수는 배포 정책상 고정. CPU/메모리도 하드웨어 고정. 코드 레벨에서 **재기동 없이** 런타임에 바꿀 수 있는 건 스레드 풀 크기뿐입니다(`ThreadPoolExecutor.setCorePoolSize`로 동적 변경 가능). 이게 "유일한 동적 자원"인 이유.
- **부족/과다의 결과**: worker가 부족하면 요청이 큐에서 대기(지연↑), 과다하면 컨텍스트 스위칭과 스택 메모리 낭비.

## 시사점
이 슬라이드는 "왜 하필 스레드인가"라는 행동 변수 선택의 정당성을 제공합니다. 일반적인 오토스케일링 논문과 차별화되는 **현장 제약 기반 문제 정의**라는 점이 연구의 실무 적합성을 높입니다. (참고: 코드에는 인스턴스를 조절하는 `ContainerAutoscaleEnv`도 있지만, 본 발표는 운영 제약에 맞는 thread 환경을 메인으로 삼습니다.)

## 예상 질문
- *"setCorePoolSize를 실시간으로 바꿔도 안전한가?"* → Java의 ThreadPoolExecutor는 런타임 변경을 지원. 다만 급격한 변경은 진동을 유발하므로 보상의 `w_thrash`로 억제(향후 실서비스 검증 필요).

# 슬라이드 8 — 모델 ①: 큐잉 이론 기반 시뮬레이터 (M/M/c 근사)

## 화면 내용
RL은 수만 step 시행착오가 필요 → 실서버 대신 큐잉 시뮬레이터에서 학습. 자원 c개·처리율 μ → 용량 cap=c·μ, 이용률 ρ=λ/cap. ρ→1이면 대기시간 비선형 폭증. 과부하면 backlog 누적. 응답시간 공식과 backlog 동역학 코드 박스.

## 배경/원리
- **왜 시뮬레이터인가**: DQN은 buffer 10만, PPO는 rollout 4096씩 수십~수백 에피소드(1 에피소드=288 step)를 돌립니다. 수십만~수백만 step의 시행착오를 실서버에 가할 수는 없습니다(장애 위험·시간). 그래서 서버 거동을 수식으로 모사한 환경에서 학습합니다.
- **응답시간 공식 3항** (코드 `_latency`):
  ```
  W = 1/μ                        # ① 순수 처리시간
    + ρ/(cap·(1−ρ))              # ② 정상상태 큐 대기 (ρ<1일 때)
    + backlog/cap                # ③ 누적 잔여작업 소진시간
  ```
  ① 일감 하나를 처리하는 기본 시간. ② **큐잉 이론의 핵심** — 이용률 ρ가 1에 가까워지면 분모 (1−ρ)가 0으로 가서 대기시간이 **비선형 폭증**합니다(M/M/c 대기행렬의 근본 성질). 코드에선 ρ가 1을 넘는 과부하에서도 발산하지 않게 `max(1−ρ, 0.02)`로 하한을 둡니다. ③ 과거에 못 처리한 backlog를 현재 용량으로 비우는 데 걸리는 시간.
- **backlog 동역학**: `backlog = max(0, backlog + (λ − cap))`. λ가 cap을 넘는 step마다 차이만큼 쌓이고, cap이 λ보다 크면 줄어듭니다(0 하한). 이 한 줄이 "한 번 밀리면 한동안 느려지는" 실서버의 관성을 만듭니다.
- **트래픽 생성기**: 매 에피소드 패턴이 달라(위상·피크·버스트 랜덤) 정책이 특정 트래픽을 암기할 수 없습니다.

## 시사점
시뮬레이터의 충실도가 곧 학습된 정책의 현실성입니다. "단순 M/M/c가 아니라 backlog 관성까지 넣었다"는 점이 모델링의 성의를 보여줍니다. 동시에 25번(한계)에서 다룰 sim-to-real gap의 출발점이기도 합니다.

## 예상 질문
- *"M/M/c를 정확히 푼 게 아니라 근사인데 괜찮나?"* → 목적은 정확한 대기행렬 수치가 아니라 "ρ→1 폭증, 과부하 누적"이라는 **정성적 거동 재현**. 정책 학습에는 이 거동이 핵심.
- *"실제 트래픽 데이터를 안 쓴 이유?"* → 일반화를 위해 도메인 랜덤화된 합성 트래픽 사용. 실측 트래픽 기반 보정은 향후 과제(26번).

# 슬라이드 9 — 모델 ②: 강화학습 기본 구조 (Agent·State·Reward)

## 화면 내용
Agent(정책 π)와 Environment(큐잉 시뮬레이터)의 상호작용 루프. 행동 a_t를 보내면 다음 상태 s_{t+1}과 보상 r_{t+1}을 받음. 하단 표는 6차원 상태 변수와 "왜 관측하는가".

| 상태 변수 | 의미 — 왜 관측하는가 |
|---|---|
| λ (트래픽) | 현재 요청 도착률, λ_max로 정규화 — 지금 부하의 크기 |
| Δλ (추세) | 직전 step 대비 증감 — 피크가 '오는 중'인지 → 선제 대응 근거 |
| ρ (이용률) | λ÷용량 — 1에 가까울수록 큐 폭증 직전 위험 신호 |
| W/SLA (지연) | 응답지연÷SLA — 1 넘으면 SLA 위반, 품질 상태 |
| c (thread 수) | 현재 자원량, c_max로 정규화 — 과거 행동들의 누적 결과 |
| backlog (잔여작업) | 못 처리해 쌓인 작업 — 과거 여파를 담아 MDP 성립 |

## 배경/원리
실제 코드 `_obs()`가 반환하는 6개 값과 정확히 일치합니다:
```python
[lam/lam_max,                       # ① 부하 크기
 (lam − lam_prev)/lam_max,          # ② 추세(1차 차분)
 min(rho, 2.0),                     # ③ 이용률 (2배로 클리핑)
 min(latency/sla, 5.0),             # ④ SLA 대비 지연 (5배로 클리핑)
 c/c_max,                           # ⑤ 현재 스레드 비율
 min(backlog/capacity(c_max), 5.0)] # ⑥ 정규화 backlog
```
- **각 변수의 역할 분담**: ①은 절대 부하, ②는 부하의 미분(방향). ②가 핵심인데, "지금 트래픽이 오르는 중"임을 알아야 **피크 도착 전에 선제 증설**할 수 있습니다. ①만 있으면 항상 사후 대응이 됩니다.
- **③ 이용률 ρ**: λ를 현재 용량으로 나눈 값. 8번에서 본 것처럼 ρ→1이 지연 폭증의 신호라, 위험을 미리 감지하는 가장 직접적인 변수.
- **⑥ backlog가 MDP를 완성**: backlog가 없으면 같은 (λ, c)인데도 과거 이력에 따라 미래가 달라져 마르코프 성질이 깨집니다. backlog를 상태에 넣음으로써 "현재 상태만 보면 미래를 예측 가능"한 MDP가 성립합니다.
- **정규화·클리핑**: 모든 값을 0~1(또는 0~몇) 범위로 정규화해 신경망 학습을 안정화하고, 극단값을 클리핑해 폭주를 막습니다.

## 시사점
상태 설계는 "에이전트가 무엇을 볼 수 있는가"를 정하는, 성능을 좌우하는 결정입니다. 특히 Δλ(추세)와 backlog(이력)를 넣은 것이 "선제 대응"과 "MDP 성립"이라는 두 가지를 가능하게 한 핵심 설계입니다.

## 예상 질문
- *"왜 6개인가, 더 넣으면?"* → 필요충분한 최소 집합을 목표. 시간(t)을 안 넣은 건 시계가 아니라 부하 자체에 반응하는 일반적 정책을 학습시키기 위함.

# 슬라이드 10 — 모델 ③: 보상 설계 — 어떤 행동이 보상받는가

## 화면 내용
보상식: `r = −1.0·(SLA초과비율) − 0.30·(c−16)⁺/48 − 0.2·(16−c)⁺/16 − 0.02·(행동변경)`. 4가지 상황(◎ 기본값 유지=페널티0 / ○ 선제 증설=소액 / ✕ SLA 위반=큰 페널티 / △ 과소·잦은변경=억제).

## 배경/원리
실제 코드 `step()`의 보상 4개 항을 그대로 풀면:
```python
sla_excess = max(0, (latency − sla)/sla)          # SLA 초과 비율
cost  = max(0, c − c_base) / (c_max − c_base)      # 기본값(16) 초과분 비용
under = max(0, c_base − c) / c_base                # 기본값 미만 페널티
r = −w_sla·min(sla_excess,5) − w_cost·cost − w_under·under − w_thrash·|Δ|/c_step
```
가중치(config.py): `w_sla=1.0, w_cost=0.30, w_under=0.2, w_thrash=0.02`, `c_base=16`.

- **① SLA 항 (−1.0×, 최대 −5)**: 가장 비싼 항. 지연이 SLA(0.2초)를 초과한 비율에 비례. `min(·,5)`로 상한을 둬 한 번의 폭증이 학습을 망치지 않게 합니다. 이 항이 압도적으로 크기 때문에 **에이전트는 무엇보다 SLA 준수를 1순위로 학습**합니다.
- **② 비용 항 (−0.30×)**: 핵심 설계는 **c_base(16) 초과분에만 과금**한다는 점. 16개까지는 비용 0이고, 그 이상 증설한 만큼만 (c−16)/48로 비례 과금. 이게 "평소엔 기본값, 피크에만 증설"을 유도하는 장치입니다.
- **③ 과소 항 (−0.2×)**: 16 미만으로 줄이면 페널티. 비용을 아끼려 무작정 줄여 안전 여유를 훼손하는 걸 막습니다.
- **④ 진동 항 (−0.02×)**: 행동을 바꿀 때마다(±4) 소액 페널티. 매 step 늘렸다 줄였다 하는 thrashing을 억제.
- **비대칭의 핵심**: SLA 위반(최대 −5)이 증설 비용(최대 −0.30)보다 **10배 이상 비쌉니다**. 그래서 "확신이 없으면 증설하는 게 이득"이라는 보수적(안전 우선) 정책이 자연스럽게 학습됩니다.

## 시사점
"보상 설계 = 운영 정책 설계"라는 명제의 구체적 증거입니다. 가중치 4개의 상대적 크기가 곧 "SLA 최우선, 비용은 차선, 진동은 미세 억제"라는 운영 철학을 인코딩합니다. 24번 분석에서 DQN의 실제 거동(평균 비용 0.13)이 이 설계대로 나왔음을 확인합니다.

## 예상 질문
- *"가중치는 어떻게 정했나?"* → SLA:비용 = 1:0.3은 "SLA가 비용보다 약 3배 중요"하다는 운영 판단을 반영. `hp_search.py`로 탐색 가능하지만, 본질은 운영자가 정하는 정책 파라미터.
- *"보상 해킹(reward hacking) 위험은?"* → 과소 항·진동 항이 극단적 꼼수(무조건 최소 유지, 매 step 토글)를 차단.

# 슬라이드 11 — 모델 ④: MDP 정의 (비단조 용량)  ★핵심

## 화면 내용
State(6,)·Action(3)·Reward 요약 + 비단조 용량 강조. c≤32: 병렬화 이득으로 용량↑. c>32: 컨텍스트 스위칭·CPU 경합으로 용량↓. 코드 박스(overhead 식)와 실측 곡선(c≈39 정점).

## 배경/원리
- **Action 공간**: `Discrete(3)` — 0(스레드 −4), 1(유지), 2(스레드 +4). `c_step=4`. 한 번에 ±4씩만 움직이므로 급격한 변화가 불가능하고, 여러 step에 걸쳐 점진 조절합니다(c 범위는 4~64).
- **비단조 용량 재확인**: 
  ```python
  overhead = 1 + alpha·max(0, c − knee)²/knee²   # alpha=2, knee=32
  capacity = c·mu_thread / overhead              # mu_thread=25
  ```
  c≤32: overhead=1, 용량=25c로 선형 증가. c>32: overhead가 (c−32)²에 비례해 증가. 미분으로 정점을 구하면 c≈39 부근에서 용량 최대, 이후 감소. **이게 룰 기반의 함정**입니다.
- **왜 룰 기반이 함정에 빠지나**: HPA식 룰은 "ρ>0.7이면 무조건 증설"합니다. 그런데 이미 c가 39를 넘은 상태에서 ρ가 높다고 또 증설하면, 용량이 **줄어들어** ρ가 더 올라가고, 룰은 또 증설하는 악순환(증설할수록 악화)에 빠질 수 있습니다. RL은 backlog·지연 신호를 종합해 "여기서 더 늘리면 손해"를 학습할 수 있습니다.

## 시사점
5번에서 제기한 "비단조성" 주장을 MDP 수준에서 구체화하고, 룰 기반 대비 RL의 우위가 **어디서** 나오는지(함정 회피)를 예고합니다. 23번 결과표에서 DQN이 룰 기반보다 적은 비용으로 같은 SLA를 낸 것이 이 함정 회피의 정량적 증거입니다.

## 예상 질문
- *"knee=32, alpha=2의 근거?"* → IO-bound 워크로드에서 CPU 코어 수의 수 배까지는 병렬화 이득, 그 이상은 CS 비용 지배라는 경험칙을 파라미터화. 정확한 값보다 "정점이 존재한다"는 구조가 핵심.

# 슬라이드 12 — 알고리즘 ①: DQN (Double DQN)

## 화면 내용
가치 기반 off-policy. Q(s,a) 학습, argmax로 행동. Q넷=MLP(state→64→64→3). Experience Replay(5만), Target Network(500 step sync), Double DQN, ε-greedy(1.0→0.05). 코드 박스(Double DQN 타깃).

## 배경/원리
실제 코드(`agents/dqn.py`)와 config 기준 상세:
- **Q 네트워크**: `MLP(n_actions, hidden, activation="relu")` — 입력 6차원 → hidden(config는 128) → hidden → 3. ReLU 활성화. DeZero로 구현, Adam 옵티마이저(lr=5e-4).
- **Experience Replay** (`ReplayBuffer`, capacity 10만): 매 step의 transition (s,a,r,s',done)을 저장하고 무작위 배치(128) 샘플링. **두 효과** — ① 연속한 step은 강한 시계열 상관이 있는데, 무작위 샘플링이 이를 끊어 학습을 안정화. ② **드문 위기 경험(backlog 폭증)을 버퍼에 오래 보존**해 반복 학습. 이게 24번에서 DQN이 PPO를 이긴 핵심 이유로 해석됩니다.
- **Target Network**: 타깃 계산용 별도 네트워크를 두고 `target_update`(config 1000) step마다 online 네트워크를 복사(`copy.deepcopy`). 타깃이 매 step 흔들리면 "움직이는 과녁"을 쏘는 셈이라 발산하므로, 고정된 타깃으로 안정화.
- **Double DQN** (코드 한 줄 차이):
  ```python
  a_next = self.q(s2).data.argmax(axis=1)          # 행동 선택: online
  q_next = self.target(s2).data[arange(B), a_next]  # 평가: target
  y = r + gamma·(1−done)·q_next
  ```
  일반 DQN은 타깃을 `max_a Q_target(s',a)`로 계산해 Q값을 **과대추정**하는 경향이 있습니다. Double DQN은 행동 선택(online)과 평가(target)를 분리해 이 편향을 완화합니다.
- **ε-greedy**: ε이 1.0에서 0.05로 선형 감쇠(전체 step의 50% 지점까지). 초반엔 무작위 탐험, 후반엔 학습된 정책 활용.
- **gradient clipping**: DeZero에 없어 `clip_grads`로 global-norm 10.0 직접 구현.

## 시사점
이 문제에 DQN이 맞는 이유는 **이산 행동(3개)** + **replay의 위기 경험 보존**입니다. 행동이 적어 Q값 비교가 명확하고, replay가 드문 과부하를 잊지 않게 합니다.

## 예상 질문
- *"왜 Double DQN까지?"* → 일반 DQN의 Q 과대추정이 비단조 환경에서 "증설하면 좋다"는 잘못된 낙관으로 이어질 수 있어, 이를 완화하는 Double DQN을 채택.

# 슬라이드 13 — 알고리즘 ②: PPO (Actor-Critic·Clipped Surrogate)

## 화면 내용
정책 경사 on-policy·Actor-Critic. π(a|s) 직접 최적화. Actor·Critic 분리 MLP. GAE(λ=0.95), Clipped objective(ε=0.2), Entropy bonus(0.01), rollout 2048(코드는 4096)·10 epoch. 코드 박스(PPO 손실).

## 배경/원리
실제 코드(`agents/ppo.py`)·config 기준:
- **Actor-Critic 분리**: Actor `MLP(n_actions, ...)`는 행동 확률(로짓)을, Critic `MLP(1, ...)`는 상태가치 V(s)를 출력. tanh 활성화, 각각 별도 Adam(lr=3e-4). 분리 옵티마이저라 가치 손실이 정책을 흔들지 않습니다.
- **GAE(λ=0.95)** (코드의 역방향 루프):
  ```python
  delta = r[t] + γ·V[t+1]·nonterminal − V[t]
  gae   = delta + γ·λ·nonterminal·gae
  adv[t] = gae
  ```
  단순히 한 step만 보면(λ=0) 분산은 작지만 편향이 크고, 끝까지 보면(λ=1) 편향은 작지만 분산이 큽니다. GAE는 λ=0.95로 그 사이 균형점을 잡아 **advantage 추정의 분산을 줄입니다**. 이후 `adv = (adv−mean)/std`로 정규화해 학습 안정화.
- **Clipped Surrogate** (PPO의 심장):
  ```python
  ratio = exp(logπ_new − logπ_old)
  surr1 = ratio·A
  surr2 = clip(ratio, 1−ε, 1+ε)·A      # ε=0.2
  L = min(surr1, surr2)
  ```
  정책이 한 번에 너무 크게 바뀌면(ratio가 1에서 멀어지면) 학습이 불안정합니다. clip이 갱신 비율을 [0.8, 1.2]로 제한해 "신뢰 구간 안에서만" 정책을 갱신합니다. **DeZero에 element-wise min이 없어**, `take1 = (surr1.data ≤ surr2.data)` 마스크로 더 작은 쪽을 선택하는 방식으로 직접 구현 — min의 기울기가 "작은 쪽으로만 흐른다"는 성질과 수학적으로 동일.
- **Entropy bonus(0.01)**: 정책 분포의 엔트로피를 손실에 더해(−0.01·H) 너무 빨리 결정적으로 수렴(탐험 소실)하는 걸 막습니다.
- **데이터 재사용**: rollout(4096 step) 수집 후 10 epoch × minibatch 256으로 반복 학습. on-policy지만 clip 덕에 같은 데이터를 안전하게 여러 번 씁니다.

## 시사점
PPO는 확률적 정책을 안정적으로 최적화하는 현대 표준입니다. DQN과의 비교 관전 포인트는 "on-policy(현재 정책 데이터만)인 PPO가 드문 위기 상태를 얼마나 잘 다루는가"인데, 결과적으로 이 부분에서 replay를 가진 DQN에 밀립니다(24번).

## 예상 질문
- *"PPO가 보통 더 강력하다는데 왜 여기선 DQN이 이겼나?"* → on-policy라 위기 경험을 모아두지 못하고, 행동이 3개뿐이라 PPO의 강점(복잡한 정책 표현)이 덜 발휘됨. 24번 상술.

# 슬라이드 16 — 프로그램 소스: 환경 핵심 (step 함수)

## 화면 내용
`capacity()`와 `step()` 코드. 행동→상태전이→보상 전 과정이 20줄 내외. 3가지 설계 의도(비단조 용량, backlog, c_base 기준 비용).

## 배경/원리
step 함수의 처리 순서(코드 그대로):
1. **행동 해석**: `delta = (action−1)·c_step` → −4/0/+4. `c = clip(c+delta, 4, 64)`.
2. **용량·backlog 갱신**: `cap = capacity(c)`; `backlog = max(0, backlog + (λ−cap))`. 과부하분 누적.
3. **지연 계산**: `latency = _latency(λ)` (8번의 3항 공식).
4. **보상 계산**: SLA 초과 + 초과증설 비용 + 과소 + 진동 (10번 식).
5. **상태 반환**: 다음 `_obs()`, 마지막 step이면 `_obs_last()`로 인덱스 보호.

세 설계 의도:
- **비단조 용량** — 늘리는 행동이 항상 이득이 아닌 함정.
- **backlog** — 과부하 여파가 다음 step으로 전이되어 MDP를 만듦.
- **c_base 기준 비용** — 평소 기본값 유지, 피크에만 증설 유도.

## 시사점
환경 전체 동역학이 20줄 내외로 압축돼 있다는 건 모델이 **투명하고 검증 가능**하다는 뜻입니다. 블랙박스가 아니라 "어떤 가정 위에 정책이 학습됐는지"를 코드로 명확히 추적할 수 있습니다.

# 슬라이드 17 — 프로그램 소스: DQN 학습 루프

## 화면 내용
`learn()` 함수 코드. 타깃 y는 .data로 기울기 차단, Double DQN 한 줄 차이, gradient clipping 직접 구현, config 일괄 관리.

## 배경/원리
- **기울기 차단(`.data`)**: 타깃 y를 만들 때 `self.q(s2).data`, `self.target(s2).data`처럼 `.data`로 접근해 계산 그래프에서 분리합니다. 타깃은 "정답"으로 고정돼야 하고, 학습 대상은 `Q(s,a)`뿐입니다. 만약 타깃에도 기울기가 흐르면 학습이 불안정해집니다.
- **손실**: `loss = Σ(Q(s,a) − y)²/B` — TD 오차의 MSE. `F.get_item`으로 실제 취한 행동 a의 Q값만 추출.
- **갱신**: `cleargrads → backward → clip_grads(10.0) → opt.update()`. DeZero 자동미분으로 역전파, global-norm clipping 후 Adam 갱신.
- **타깃 동기화**: `step_count % target_update == 0`일 때 online을 target으로 복사.
- **학습 시작 지연**: `learn_start`(2000) step까지는 버퍼만 채우고 학습 안 함 — 초기 무작위 데이터로 섣불리 학습하지 않도록.

## 시사점
"알고리즘을 직접 구현했다"의 핵심 증거 슬라이드. Double DQN의 차이가 단 한 줄(`a_next`를 online에서 선택)이라는 점, gradient clipping을 라이브러리 없이 짠 점이 이해도를 보여줍니다. 발표 시 시간이 부족하면 한 문장("Double DQN 타깃을 직접 구현")으로 압축 가능.

# 슬라이드 18 — 프로그램 소스: PPO 업데이트

## 화면 내용
GAE(λ) 역방향 계산 + Clipped surrogate 코드(선택 마스크). advantage 정규화, actor·critic 분리 옵티마이저.

## 배경/원리
- **GAE 역방향 루프**: 마지막 step부터 거꾸로 누적해 각 시점의 advantage를 계산. `nonterminal`로 에피소드 경계에서 보상 전파를 차단.
- **min 직접 구현**: 핵심 트릭. DeZero엔 element-wise min이 없어
  ```python
  take1 = (surr1.data ≤ surr2.data)   # 더 작은 쪽 마스크(상수)
  pi_loss = −Σ(surr1·take1 + surr2·(1−take1))/m
  ```
  마스크는 상수라 기울기가 안 흐르고, 실제로 선택된 항(더 작은 surrogate)으로만 기울기가 흐릅니다 → `min`의 기울기와 동일.
- **advantage 정규화**: `(adv−mean)/std`로 스케일을 맞춰 학습률 민감도를 낮춤.
- **분리 옵티마이저**: actor·critic을 각각 갱신해 가치 손실의 큰 기울기가 정책을 교란하지 않도록.

## 시사점
PPO의 가장 까다로운 부분(clipped min)을 프레임워크 한계 안에서 수학적으로 동등하게 구현했다는 점이 구현 역량을 보여줍니다. 17번과 함께 "밑바닥 구현"의 양대 증거.

하이퍼파라미터 표(학습량, DQN/PPO 설정, 네트워크, 평가 프로토콜, 지표)와 컴퓨팅(CPU 수 분, hp_search.py).

# 슬라이드 20 — 과적합 방지 설계

## 화면 내용
3가지: ①시드 3분할(학습/검증/평가 완전 분리) ②검증 기반 best 체크포인트 ③도메인 랜덤화.

## 배경/원리
RL에서도 "본 적 없는 상황에서의 일반화"가 중요하며, 본 프로젝트는 지도학습의 train/val/test 원칙을 그대로 적용했습니다.
- **① 시드 3분할** (config.py):

  - 평가: `EVAL_SEED(7777) + i`
  세 집합이 **절대 겹치지 않습니다**. 특히 평가 시드는 하이퍼파라미터 튜닝에도 쓰지 않아, 평가가 진짜 "처음 보는 트래픽"에서의 성능입니다.
- **② 검증 기반 best 체크포인트** (train.py): VAL_INTERVAL(10) 에피소드마다 검증 트래픽에서 greedy 평가 → 최고 성능 시점의 가중치를 `*_best`로 별도 저장. **학습 후반의 정책 붕괴**(과거 PPO 실험에서 관찰됨)가 최종 모델을 오염시키지 않습니다. evaluate.py는 항상 best를 사용.
- **③ 도메인 랜덤화** (traffic.py): 위상·피크 크기·버스트 위치·강도가 매 에피소드 무작위. 특정 패턴을 암기한 정책은 검증에서 자동으로 걸러집니다.

## 시사점
이 슬라이드는 채점자가 가장 좋아할 부분입니다 — "결과가 운이나 암기가 아니라 일반화된 성능"임을 방법론으로 보증합니다. 머신러닝 연구의 엄밀성을 갖췄다는 신호.

## 예상 질문

# 슬라이드 21 — 결과 ①: 학습 곡선

## 화면 내용
실선=학습 보상(10-ep 이동평균), 점선=검증 트래픽 보상. 검증 최고점에서 best 저장. 관전 포인트(수렴 수준, DQN 점진 vs PPO 빠른 수렴). 수렴 후 출렁임은 트래픽 난이도 차 때문(정상).

## 배경/원리
- **두 곡선의 의미**: 실선(학습 보상)이 오르는 건 당연하지만, 점선(검증 보상)이 함께 올라야 진짜 학습입니다. 점선이 떨어지면 과적합 신호인데, best 체크포인트가 점선 최고점을 잡습니다.

- **수렴 후 출렁임**: 에피소드마다 버스트 수·크기가 달라 "쉬운 날/어려운 날"이 섞입니다. 어려운 에피소드는 보상이 낮게 나오므로 곡선이 출렁이는 게 정상 — 발산이나 불안정이 아닙니다.

## 시사점
학습이 됐다는 1차 증거이자, best 체크포인트 전략(20번)이 실제로 작동함을 시각적으로 보여줍니다. "출렁임 = 트래픽 난이도 차이"라는 해명을 미리 해두면 Q&A 방어가 됩니다.

# 슬라이드 22 — 결과 ②: 같은 트래픽에서의 정책 거동

## 화면 내용
3단 그래프(위: 트래픽 / 가운데: worker thread 수 / 아래: 응답 지연, 빨간선=SLA). 확인 포인트 ①기본값 유지→피크 증설→복귀 ②무작정 안 늘림(함정 회피) ③룰의 사후 지연 스파이크 vs RL 선제 대응. Static은 버스트마다 SLA 붕괴.

## 배경/원리
이 그래프는 **숫자(23번)가 아니라 행동의 질**을 보여줍니다.
- **기본값 부근 유지**: RL이 평소 16 근처에 머무는 건 보상 설계(10번)의 c_base 효과가 실제로 작동한다는 증거. 비용 페널티 때문에 불필요하게 안 늘립니다.
- **피크 선제 증설 후 복귀**: 트래픽(위)이 오르기 시작하면 스레드(가운데)가 미리 올라가고, 피크가 지나면 다시 내려옵니다. Δλ(추세) 관측(9번)이 선제 대응을 가능하게 한 것.
- **함정 회피**: 스레드를 39 이상으로 무작정 안 늘립니다 — 비단조 용량(11번)의 함정을 학습으로 피한 모습.
- **룰 vs RL의 결정적 차이**: 룰 기반은 ρ가 임계값을 넘은 **후에야** 반응하므로 지연(아래)에 스파이크가 생깁니다(사후 대응). RL은 미리 대응해 지연이 평탄.
- **Static(회색)**: 16 고정이라 버스트마다 용량이 부족해 지연이 SLA를 크게 넘습니다(SLA선 위로 치솟음).

## 시사점
23번의 종합 수치가 "왜" 그렇게 나오는지를 한 장으로 설명합니다. 정량(표)과 정성(거동)을 함께 제시하는 게 설득력의 핵심. 특히 "선제 vs 사후"는 RL의 본질적 우위를 직관적으로 보여주는 그림입니다.

# 슬라이드 23 — 결과 ③: 정책 종합 비교  ★핵심

## 화면 내용
evaluate.py 출력(threadpool_summary.csv), 평가 전용 시드 20 에피소드, 비용은 c_base(16) 초과분 기준.

| 정책 | 보상 | SLA 위반률 | 자원 비용 | 평균 지연 |
|---|---|---|---|---|
| **DQN** | **−44.9** | 3.1% | **0.130** | 151 ms |
| PPO | −60.7 | 3.1% | 0.273 | 155 ms |
| Rule-based | −65.8 | 3.5% | 0.288 | 182 ms |
| Static | −652.9 | 50.3% | 0.000 | 4,218 ms |

## 배경/원리 (수치 정밀 해석)
- **DQN이 전 지표 1위**: 보상 −44.9로 최고, SLA 위반 3.1%, 비용 0.130, 지연 151ms.
- **핵심 메시지 ①(DQN vs 룰)**: SLA 위반률은 DQN 3.1% vs 룰 3.5%로 **거의 동등**한데, 자원 비용은 0.130 vs 0.288로 **DQN이 약 45%(절반 이하)**. 즉 같은 품질을 절반 비용에 — 이게 11번에서 예고한 "비단조 함정 회피"의 정량적 결실입니다. 룰은 ρ만 보고 과증설하지만 DQN은 비용을 의식하며 필요한 만큼만 증설.
- **핵심 메시지 ②(DQN vs PPO)**: SLA는 동일(3.1%)하지만 PPO의 비용이 0.273으로 DQN의 2배. PPO도 룰보다는 낫지만(보상 −60.7 > −65.8), DQN이 더 효율적인 운영점에 수렴.
- **핵심 메시지 ③(Static의 붕괴)**: SLA 위반 50.3%, 평균 지연 4,218ms(약 4.2초!). 비용은 0이지만(증설 안 하니까) 절반의 시간 동안 SLA를 위반해 보상이 −652.9로 압도적 최악. **동적 제어가 선택이 아니라 필수**임을 증명.

## 시사점
발표 전체에서 **가장 중요한 한 장**입니다. "DQN은 룰 기반과 같은 SLA를 절반 비용으로"라는 한 문장이 프로젝트의 결론입니다. Static의 4.2초 지연은 동적 제어의 가치를 극적으로 보여주는 숫자.

## 예상 질문
- *"Static의 비용이 0인데 왜 최악?"* → 비용은 c_base 초과 증설분 기준이라 16 고정이면 0이지만, SLA 위반 페널티(−1.0×, 최대 −5)가 step의 절반에서 누적돼 보상이 폭락. 비용을 0으로 만든 대가가 품질 붕괴.
- *"20 에피소드면 통계적으로 충분한가?"* → 동일 고정 시드로 4개 정책을 같은 트래픽에 노출해 비교했으므로 정책 간 상대 비교는 공정. 표본을 늘려도 순위는 안정적.

# 슬라이드 24 — 결과 분석: 세 가지 분석 축

## 화면 내용
①동적 제어 필수성(Static 격차) ②보상 설계=운영 정책(c_base 효과) ③알고리즘 특성(on vs off-policy).

## 배경/원리
- **축 1 — 동적 제어는 필수인가**: Static 50.3% vs 동적 3.1~3.5%. "튜닝 한 번 하고 방치"하는 관행의 비용이 SLA 위반 50%로 정량화됐습니다. 이론이 아니라 실측으로 확인.
- **축 2 — 보상 설계 = 운영 정책 설계**: 22번 거동에서 RL이 평소 16 유지 → 피크 증설 → 복귀를 보였고, DQN 평균 비용 0.130은 룰(0.288)의 45%. "필요할 때만 증설"이 c_base 보상 설계(10번)대로 정확히 유도됐습니다. 보상 가중치가 곧 운영 철학임을 실증.
- **축 3 — on-policy vs off-policy**: DQN(−44.9) > PPO(−60.7). 해석은 **Experience Replay**입니다. backlog 폭증 같은 위기 상태는 드물게 발생하는데, DQN은 이를 버퍼에 보존해 반복 학습합니다. PPO는 on-policy라 현재 정책이 만든 데이터만 쓰고 버려, 드문 위기를 충분히 학습하기 어렵습니다. 그 결과 비단조 함정 회피에서 DQN이 더 안정적.

## 시사점
단순히 "DQN이 이겼다"가 아니라 **왜** 이겼는지를 알고리즘 원리(replay)로 설명합니다. 이게 결과 분석의 깊이를 보여주는 부분 — 현상→원인 연결.

## 예상 질문
- *"PPO를 개선하면 이길 수 있나?"* → 위기 상태 오버샘플링, 보상 클리핑 완화, 커리큘럼 학습 등이 후보(25번 한계). 본 실험 범위에선 DQN 우위.

# 슬라이드 25 — 한계점 및 토론

## 화면 내용

## 배경/원리
- **① sim-to-real gap**: 시뮬레이터는 실제 JVM의 GC pause(가비지 컬렉션으로 인한 일시 정지), JIT 워밍업(초기 바이트코드 해석이 느림), 요청 간 의존성을 단순화했습니다. 실서버 적용 전에 실측 트래픽·지연 분포로 시뮬레이터를 보정해야 합니다.
- **② PPO 위기 학습 한계**: 본 실험에서 미해결. 위기 상태 오버샘플링, 보상 정형화(clipping 완화), 커리큘럼 학습(쉬운→어려운 순서) 등이 후보.
- **③ 행동 공간 단순화**: ±4/유지의 3개 이산 행동. 연속 제어(SAC)나 가변 폭 조절은 미실험 — 더 세밀한 제어 가능성.
- **④ 단일 서비스 가정**: 실제 MSA는 서비스 간 의존이 있어 한 서비스의 병목이 다른 서비스로 전파됩니다. 멀티에이전트로의 확장이 필요.

## 시사점
