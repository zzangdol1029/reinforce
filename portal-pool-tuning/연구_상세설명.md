# 강화학습 기반 포털 WAS 자원(워커 스레드풀 + DB 커넥션풀) 동적 동시 튜닝
## 연구 방향 및 내용 상세 설명서

---

## 0. 한 줄 요약

> 실제 MSA 포털 시스템(고정·단일 서버, Spring Boot/Undertow)에서 **현재 정적으로 박아둔 자원 설정(워커 스레드 수 · DB 커넥션풀 크기)**이 부하·요청 특성 변화에 못 맞춰 비효율적이라는 점에 착안하여, **관측 가능한 운영 지표만으로 두 자원을 실시간·선제적으로 조절하는 정책(모델)을 강화학습(DQN·PPO·SAC)으로 학습**한다. 핵심 산출물은 "상황(상태) → 최적 자원량(행동)"을 출력하는 학습된 정책이며, 미래·은닉 정보를 쓰는 이론적 상한(Oracle)에 근접하도록 학습해 현재 설정 대비 메모리를 크게 절감하면서 SLA를 유지하는 것을 목표로 한다.

**키워드**: 강화학습, 자원 자동 튜닝(auto-tuning), MSA, Undertow 워커풀, HikariCP 커넥션풀, 결합 병목, 부분관측, 시뮬레이터 기반 학습, sim-to-real, DQN/PPO/SAC

## 1. 연구 배경 및 동기

### 1.1 문제가 되는 현장 상황

운영 중인 MSA 포털 시스템은 `nginx(WEB) → Gateway/Eureka → Undertow(WAS)` 구조이며, 세 개의 포털(사용자·연구·관리)이 각각 독립된 고정 서버에서 운영된다. 각 WAS는 두 가지 핵심 자원을 **정적 설정값으로 고정**해 둔다.

- **Undertow 워커 스레드 수(W)**: 요청을 처리하는 블로킹 작업 스레드 풀 크기. 예) 연구포털 `SERVER_UNDERTOW_WORKER_THREADS=2048`.
- **HikariCP DB 커넥션풀 크기(D)**: DB 질의에 사용하는 커넥션 수. 예) 연구포털 `maximum-pool-size=150`.

이 값들은 한 번 정하면 운영 내내 고정된다. 그러나 실제 부하(초당 요청 수)와 **요청의 성격(요청 믹스: CPU 위주인지 DB 위주인지, 체류시간이 긴지 짧은지)**은 시간대·업무 패턴에 따라 크게 변동한다.

### 1.2 정적 설정의 비효율 (양방향 오류)

고정값은 변하는 최적값을 따라갈 수 없어 **두 방향 모두에서 손해**가 발생한다.

1. **과다 설정 → 메모리·자원 낭비**: 워커 스레드는 각자 스택 메모리와 요청 컨텍스트를 점유한다. 부하가 낮거나 요청이 가벼운 대부분의 시간 동안 2048개의 워커는 명백히 과다하며, JVM 힙·메모리를 낭비하고 컨텍스트 스위칭 오버헤드를 키운다.
2. **과소 설정 → 병목·지연**: 반대로 DB 위주의 무거운 요청이 몰리는 구간에서는 커넥션풀이 부족해 워커가 DB 커넥션을 기다리며 묶이고, 응답 지연이 급증한다.

즉 **하나의 고정값으로는 "한가할 때의 절약"과 "몰릴 때의 안정성"을 동시에 달성할 수 없다.** 또한 인프라가 고정·단일 서버라 인스턴스를 늘리는 수평 스케일링도 불가능하다. 그러므로 **주어진 고정 용량을 가장 잘 쓰는 소프트웨어 제어 노브(워커풀·DB풀 크기)를 부하에 맞춰 동적으로 조절**하는 것이 현실적이고 효과적인 개선 방향이다.

### 1.3 왜 지금 이 연구가 의미 있는가

- 실제 자원설정 데이터(엑셀)에서 **연구포털이 워커 2048개를 정적 고정**하고 있음을 확인했다. 이는 곧 "현실의 과프로비전 사례"이며, 본 연구가 직접 겨냥하는 개선 대상이다.
- 두 자원(워커·DB)이 **서로 결합된 병목** 관계라 한쪽만 조절해서는 안 되고, 둘을 함께 봐야 한다는 점에서 단순 규칙으로 풀기 어렵다 → 학습 기반 접근의 타당성.

## 2. 문제 정의

### 2.1 결정 문제

> **매 제어 주기(예: 수~수십 초)마다, 관측된 운영 지표를 보고 Undertow 워커 스레드 수(W)와 HikariCP DB 커넥션 수(D)를 얼마로 조절할지 결정한다.** 목표는 SLA(응답시간/드롭)를 지키면서 자원 비용(메모리·DB 부하)을 최소화하는 것이다.

### 2.2 결합 병목 구조 (이 연구의 핵심 물리)

한 요청의 생애주기:

1. 요청이 들어오면 **워커 스레드 1개를 전체 체류시간 동안 점유**한다.
2. 그 중 DB 질의 단계에서는 **추가로 DB 커넥션 1개를 점유**한다(없으면 대기).
3. CPU 연산 단계에서는 **CPU 코어**를 사용한다.

따라서 시스템의 처리능력은 세 자원 중 **가장 작은 것(병목)**으로 결정된다.

```
처리능력(capacity) = min( CPU한계,  워커한계,  DB한계 )
                   = min( C / cpu_time,  W / 체류시간,  D / db_time )
```

- 워커만 늘려도 **DB풀이 작으면** 워커가 DB 커넥션 대기로 묶여 소용없다.
- DB풀을 무작정 키우면 **공유 통합 DB(Postgres, 최대 1500 커넥션)가 과부하**되어 DB 자체가 느려진다.
- 그러므로 **W와 D를 함께(동시에) 최적화**해야 한다.

### 2.3 핵심 난점 (왜 단순하지 않은가)

1. **부분관측(은닉 변수)**: 요청 믹스(체류시간 분포, DB 비중)는 직접 측정되지 않는다. 에이전트는 CPU 이용률·워커풀 점유율·DB풀 점유율·지연 같은 **관측 가능한 지표의 추세로 추론**해야 한다.
2. **비정상성(non-stationary)**: 부하와 요청 믹스가 시간에 따라 계속 변한다 → 고정된 "정답값"이 없고, "상황에 맞는 정책"이 필요하다.
3. **순차적·예측 필요**: 자원 조절에는 변화 폭 제한·잦은 변경 비용(thrash)이 있어, 부하가 오른 뒤 반응하면 늦다. 변화를 **미리 읽어 선제적으로** 조절해야 한다.
4. **다목적 상충**: SLA(낮은 지연) ↔ 비용(적은 자원)이 상충한다.

이 네 가지 성질(부분관측·비정상·순차·다목적)이 **강화학습이 단순 규칙/정적 최적화보다 적합한 근거**다.

## 3. 연구 목표 및 연구 질문(RQ)

### 3.1 목표

관측 가능한 운영 지표만으로 워커풀·DB풀을 동적·동시 조절하는 정책을 학습하여, **현재의 정적 설정과 반응형 휴리스틱을 능가하고, 이론적 상한(Oracle)에 근접**한다.

### 3.2 연구 질문

- **RQ1 (성능)**: 학습된 RL 정책은 현재 정적 설정·반응형(HillClimb) 대비 보상(SLA+비용 종합)에서 얼마나 개선되는가?
- **RQ2 (자원 효율)**: SLA를 유지하면서 워커/DB 자원(메모리·DB 부하)을 얼마나 절감하는가?
- **RQ3 (알고리즘 비교)**: DQN·PPO·SAC의 수렴 속도·안정성·최종 성능은 어떻게 다른가? 이산(Discrete) vs 연속(Box) 행동공간의 영향은?
- **RQ4 (상한 근접도)**: 미래·은닉 정보를 쓰는 Oracle 대비 RL이 얼마나 근접하는가? (관측만으로 도달 가능한 한계)
- **RQ5 (포털별 특성)**: 병목 구조가 다른 세 포털(워커/DB 병목 vs CPU 병목 vs 여유)에서 정책이 어떻게 달라지는가?

## 4. 관련 연구 / 배경 지식

- **시스템 자원 자동 튜닝(auto-tuning)**: DB 파라미터 튜닝(OtterTune), JVM/스레드풀 튜닝 등. 본 연구는 "동적·온라인" 튜닝이며 두 자원 결합이 특징.
- **RL for Systems**: 데이터센터 냉각(구글 DeepMind), 클러스터 스케줄링(DeepRM), 적응형 동시성 제어(Netflix/Envoy adaptive concurrency) 등 시스템 제어에 RL을 적용한 사례. 거의 모두 **시뮬레이터/모델 기반 학습 후 배포** 방식.
- **오토스케일링과의 차이**: 오토스케일링은 "인스턴스 수"를 늘리는 수평 확장(스케일링 가능 환경 전제). 본 연구는 **스케일링 불가(고정·단일 서버) 환경에서 소프트웨어 노브를 튜닝**한다는 점이 다르다.
- **Undertow/XNIO**: Undertow는 IO 스레드(비동기 수락)와 워커 스레드(블로킹 처리) 풀로 구성. `worker-threads`가 본 연구의 튜닝 대상.
- **HikariCP**: 고성능 JDBC 커넥션풀. `maximum-pool-size`가 튜닝 대상이며, `hikaricp.connections.active/idle/pending` 메트릭을 직접 노출한다(관측성 우수).
- **sim-to-real**: 시뮬레이터에서 학습한 정책을 실제에 옮길 때의 격차. 본 연구의 핵심 한계이자 향후 보정 과제.

## 5. 왜 강화학습인가 (대안 비교)

| 접근 | 한계 | 본 문제 적합성 |
|------|------|----------------|
| **정적 고정값** | 변하는 최적을 못 따라감 | ✕ (현재 방식 = 개선 대상) |
| **규칙 기반(임계값)** | 임계값을 사람이 정해야 하고 전환 구간에서 뒤처짐 | △ (반응형 베이스라인 HillClimb) |
| **그리드 탐색/최적화** | 현재·미래 상태(은닉 믹스 포함)를 모두 알아야 가능 → 운영에선 불가, 일반화 불가 | ✕ (단, 상한 참조 Oracle로 활용) |
| **지도학습(로그→최적)** | 운영 로그엔 "가본 설정"만 존재(반사실 부재) → 탐색 부족 | △ (offline RL로 확장 가능) |
| **MPC(모델예측제어)** | 정확한 동역학 모델 + 실시간 최적화 필요 | △ (모델 정확 시 대안) |
| **강화학습(정책 학습)** | 시뮬레이터 충실도에 의존 | ◎ (부분관측·비정상·순차·다목적에 부합) |

**핵심**: 그리드 탐색(=Oracle)은 "최적값을 찾는" 것이지만 **미래·은닉 정보를 쓰는 치트**이므로 배포 불가능한 상한이다. RL은 "값"이 아니라 **관측만으로 작동하는 정책(함수)**을 학습하므로, 실제 배포 가능한 해를 만든다. 이것이 본 연구가 단순 최적화가 아니라 강화학습인 이유다.

## 6. 방법론 — MDP(마르코프 결정 과정) 정형화

제어를 일정 주기마다의 의사결정으로 보고 MDP로 정형화한다.

### 6.1 State (상태) — 10차원, 모두 관측 가능한 메트릭

| 분류 | 구성 요소 |
|------|-----------|
| 부하 | 정규화 도착률(RPS), 도착률 추세(Δ) |
| 자원 점유 | CPU 이용률, **워커풀 점유율**, **DB풀 점유율** |
| 성능 | 정규화 지연, 지연 추세(Δ), 직전 드롭율 |
| 현재 설정 | W/maxW, D/maxD |

- **추세(Δ) 포함 이유**: 부드럽게 변하는 부하·믹스를 미리 읽어 선제 조절하도록.
- **점유율 포함 이유**: 워커가 병목인지 DB가 병목인지를 에이전트가 **진단**하게 함(실제 Actuator/Micrometer/HikariCP 메트릭에 대응).
- **요청 믹스(체류시간·DB비중)는 의도적으로 제외** → 비노출(부분관측). 위 관측값들로 추론.

### 6.2 Action (행동) — 두 자원 동시 조절

- **이산(DQN·PPO)**: `Discrete(25)` = ΔW 5단계 × ΔD 5단계. 각 단계는 최대값 대비 비율(예: ±8%, ±2%, 0).
- **연속(SAC)**: `Box(-1,1,(2,))` → [ΔW, ΔD]를 최대 변화폭에 매핑.
- 비율 기반 변화폭을 쓰는 이유: 포털마다 자원 규모가 매우 다르므로(연구 워커 2048 vs 관리 512) 스케일 불변적으로 만들기 위함.

### 6.3 Reward (보상)

```
Reward = − sla_weight · max(0, 지연 − SLA임계)      (SLA 위반 패널티)
         − drop_penalty · 드롭율                     (요청 손실 패널티)
         − mem_cost · W                              (워커 메모리 비용)
         − db_cost · D                               (DB 커넥션 비용)
         − thrash · (|ΔW|/maxW + |ΔD|/maxD)          (잦은 변경 안정성 패널티)
```

- 비용 계수는 `mem_cost·전형적W ≈ db_cost·전형적D ≈ SLA 페널티 스케일`이 되도록 포털별로 설계 → 에이전트가 두 자원을 **균형 있게** 조절하도록 유도.
- 한 스텝 = 한 번의 자원 재조정. 에피소드 = 200 제어 스텝.

## 7. 시뮬레이터 설계 (학습 환경)

RL은 실서버가 아니라 시뮬레이터에서 수십만 번의 시행착오로 학습한다(실서버 직접 학습은 횟수·위험 때문에 불가). 시뮬레이터는 Gymnasium 인터페이스(`reset`/`step`)로 구현한다.

### 7.1 성능 모델 `perf()` — 결합 병목 + 큐잉 지연

```
cpu_t      = (1 − db_frac) · mean_s         # 요청당 CPU 시간
db_t       = db_frac · mean_s               # 요청당 DB 점유 시간
db_t_eff   = db_t · (1 + db_contention · D / db_shared_max)   # 공유 DB 과부하 반영
mean_s_eff = cpu_t + db_t_eff               # 유효 체류시간

cpu_cap    = cores / cpu_t                   # CPU 한계 처리율
worker_cap = W / mean_s_eff                  # 워커 한계 처리율 (Little의 법칙)
db_cap     = D / db_t_eff                     # DB 한계 처리율
capacity   = min(cpu_cap, worker_cap, db_cap) # 병목 = 셋 중 최소

rho        = 도착률 / capacity                # 이용률
overhead   = overhead_coef · (max(0, W − cores)/cores)²   # 워커 과다 시 초선형 오버헤드
latency    = mean_s_eff / (1 − min(rho, 0.99)) + overhead  # M/M/1 유사 큐잉 지연
drop       = (도착률 − capacity)/도착률  (rho ≥ 1일 때)    # 용량 초과분 드롭
```

- **공유 DB 과부하**: D가 커질수록 `db_t_eff`가 증가 → DB풀을 무작정 키우면 손해(현실 반영).
- **워커 과다 오버헤드**: W가 코어 수를 크게 초과하면 컨텍스트 스위칭 비용이 초선형으로 증가.

### 7.2 워크로드 생성

- `reset()`에서 시드 기반으로 **부하(RPS)·체류시간(mean_s)·DB비중(db_frac)의 시간열(trace)**을 결정적으로 생성(일간 주기 + 변동 + 위상차).
- 시드를 바꾸면 다른 시나리오가 생성되어, 정책이 다양한 상황에 일반화되도록 학습.
- 결정적 trace 덕분에 **Oracle이 미래를 정확히 참조**할 수 있다(상한 계산용).

### 7.3 관측 메트릭(상태) 산출

`perf()`로부터 CPU 이용률·워커풀 점유율(`도착률·mean_s_eff / W`)·DB풀 점유율(`도착률·db_t_eff / D`)·지연·드롭을 계산해 상태로 제공. 이 값들이 곧 실제 운영의 측정 지표에 1:1 대응한다.

## 8. 실제 시스템 사양 반영 (3 포털 프리셋)

자원설정 데이터(엑셀)를 노드 1대 기준으로 시뮬레이터 파라미터에 반영했다.

| 포털 | 코어 | 현재 워커 | 현재 DB풀 | 동접 | 특성/병목 |
|------|------|-----------|-----------|------|-----------|
| **연구** | 256 | **2048** | 150 | 1000 | 장시간 DB 요청 多 → 워커 과다 + DB-heavy 구간 DB 부족 |
| **사용자** | 16 | 256(기본) | 100 | 5000 | 동접 많고 코어 적음 → **피크에서 CPU 병목** |
| **관리** | 32 | 512(기본) | 50 | 200 | 부하 여유 → 워커 대폭 과다 |

- 도착률(RPS)·요청 믹스는 동접·업무 특성 기반 **추정값**(노드 1대 기준)이며, 실측 보정이 향후 과제.
- 공유 통합 DB(Postgres 32c/256GB×2, max 1500)의 과부하를 모델에 반영.
- 세 포털이 서로 다른 병목(워커/DB · CPU · 여유)을 가져, 정책이 상황별로 다르게 학습되는 좋은 비교군을 형성.

## 9. 알고리즘 (DQN · PPO · SAC)

세 가지를 적용하고 비교한다(과제의 "여러 모델 비교" 요건 충족).

- **DQN (가치 기반)**: 상태-행동 가치 Q를 학습해 최적 행동 선택. 이산 행동(Discrete 25)에 적합. 빠르지만 변동이 큼.
- **PPO (Actor-Critic, 정책 기반)**: 정책을 안정적으로 갱신(클리핑). 이산 행동. 안정적·범용.
- **SAC (Actor-Critic, 연속)**: 엔트로피 정규화로 탐색·안정성 강화. **연속 행동(Box 2차원, ΔW·ΔD)**에 적합.

**비교 관점**: 동일 시나리오/시드에서 학습 후 평균 보상·SLA·자원사용량으로 비교하고 가장 좋은 알고리즘을 채택. 이산 vs 연속 행동공간의 영향, 수렴 속도·안정성 차이도 분석. 라이브러리는 PyTorch 기반 Stable-Baselines3.

---

## 10. 베이스라인 설계 (비교 기준)

| 베이스라인 | 의미 | 역할 |
|------------|------|------|
| **Static-Current** | 현재 운영 정적 설정(연구 2048/150 등) | **핵심 비교 대상** — RL이 이걸 이겨야 함 |
| **Static-Max** | 둘 다 최대(완전 과프로비전) | 안전하지만 낭비 — 상한 비용 |
| **Static-Low** | 둘 다 작게 고정 | 싸지만 병목 — 하한 |
| **HillClimb** | 점유율·지연 보고 반응형 조절 | 반응형의 한계(전환 지연) 대조 |
| **Oracle(ref)** | 미래·은닉 정보를 알고 선행 최적 조절 | **이론적 상한**(배포 불가, RL의 목표) |

Oracle은 결정적 trace의 미래값을 참조해 향후 윈도우의 최적 (W,D)를 격자 탐색으로 구하는 **선행(anticipatory) 상한**이다. 배포 가능한 해가 아니라 "여기까지 갈 수 있다"는 천장이며, RL의 성능을 재는 기준이다.

## 12. 예상 결과 및 분석 방향

### 12.1 검증된 베이스라인 격차 (현재 설정 vs Oracle 상한)

시뮬레이터·베이스라인을 실행해 다음을 확인했다(20 에피소드 평균). **현재 설정은 모든 포털에서 비최적**이다.

| 포털 | 현재 (W/D) | Oracle (W/D) | 보상 개선 | 핵심 효과 |
|------|-----------|--------------|-----------|-----------|
| 연구 | 2048 / 150 | **328 / 143** | **+190** | 워커 84%↓ (메모리 대폭 절감) |
| 사용자 | 256 / 100 | **40 / 20** | **+715** | 과다 자원 정리 (단, CPU 병목 존재) |
| 관리 | 512 / 50 | **37 / 9** | **+259** | 거의 SLA 충족, 큰 절감 |

> ※ 위 Oracle 수치는 "미래를 아는 이상적 상한"이며 RL의 실제 결과가 아니다. RL은 관측만으로 이 상한에 **근접**하는 것을 목표로 한다.

### 12.2 RL에 기대하는 결과(학습 실행 후 채움)

- RL이 **Static-Current와 HillClimb를 능가**하고 Oracle에 근접.
- **부하·믹스 변화에 따라 W·D를 선제 조절**하는 시계열(현재 설정 점선 위아래로 탄력적 변동).
- **DQN/PPO/SAC 비교**: 일반적으로 PPO/SAC가 안정적, DQN은 빠르나 변동 큼 — 이 차이를 학습 곡선으로 제시.

### 12.3 포털별 해석 포인트

- **연구**: 워커가 거의 항상 과다 → 큰 메모리 절감. DB-heavy 장시간 요청 구간이 SLA의 주 원인.
- **사용자**: 16코어 한계로 **피크에서 CPU 병목** → 풀 튜닝만으론 SLA를 다 못 지킴. 이는 "코어/노드 증설 필요"라는 별도의 운영 인사이트(정직한 한계).
- **관리**: 부하 여유 → 가장 큰 자원 절감 여지.

## 13. 연구의 기여도

1. **실제 포털 사양 기반**의 워커풀+DB풀 **2자원 결합 동시 튜닝**을 강화학습으로 정형화·구현.
2. **현재 정적 설정 대비 메모리(워커)를 대폭 절감하면서 SLA를 유지**하는 정책의 가능성 입증.
3. **관측 가능한 메트릭만으로 병목 자원을 진단·선제 조절**하는 정책 설계(부분관측에서 배포 가능한 상태 설계).
4. 세 포털의 서로 다른 병목 구조에 대한 분석과, "사용자포털은 CPU 증설이 근본 해결책"이라는 운영 인사이트 도출.

---

## 14. 한계

1. **sim-to-real gap**: 보정되지 않은 수식 시뮬레이터에서 학습한 정책은 실제와 다를 수 있다(방법론 입증 수준). 실서버 적용엔 실측 보정·검증이 필요.
2. **추정값 의존**: 도착률·요청 믹스는 동접·업무 특성 기반 가정값. 실측(APM/부하테스트) 보정 필요.
3. **CPU 병목 포털의 한계**: 사용자포털처럼 코어가 근본 제약인 경우 풀 튜닝의 효과가 제한적.
4. **단일 노드 모델**: 공유 통합 DB를 통한 멀티포털 상호작용(여러 포털이 동시에 DB풀을 키울 때의 경합)은 단순화됨.

## 15. 향후 연구 방향 — 운영 적용 닫힌 루프(continual)

```
[1 시뮬레이터 학습] → [2 정책 배포(또는 권고)] → [3 운영 지표 수집] → [4 시뮬레이터 보정·재학습] ┐
        ▲────────────────────── 운영 데이터로 반복 개선 (continual learning) ──────────────────────┘
```

1. **시뮬레이터에서 다양한 (W,D)·상황을 탐색하며 정책 학습** (안 가본 설정도 가상으로 시도 가능).
2. **정책 배포**: 실시간 지표(Actuator/Micrometer/HikariCP)를 읽어 (W,D) 출력. 안전하게는 **운영자 승인형 어드바이저(권고) 모드**로 시작.
3. **운영 지표 수집**: 실제 점유율·지연·결과를 모니터링으로 축적.
4. **시뮬레이터 보정 + 재학습**: 실측으로 `perf()` 모델을 현실에 맞게 보정(sim-to-real 갭 축소) → 정책 재학습 → 다시 1번.

추가 확장:
- **실측 메트릭으로 시뮬레이터 보정**(디지털 트윈), **offline RL**(탐색 로그 직접 학습), **공유 DB 멀티포털 동시 최적화**, **관측 노이즈·수집 지연 반영**으로 현실성 강화.

> 이 루프가 "가상이라 의미 있나?"라는 질문에 대한 답이다: 처음엔 가상(근사)에서 출발하지만 운영 데이터로 계속 보정하며 **현실 최적에 점차 수렴**한다.

## 16. 운영 연동 — 관측 지표의 실제 출처

상태(state)에 쓰는 값은 모두 **표준 모니터링으로 측정 가능**하다(요청 믹스만 비노출 → 추론).

| 상태 변수 | 실제 출처 |
|-----------|-----------|
| CPU 이용률 | OS/컨테이너 메트릭, JVM `OperatingSystemMXBean` |
| 워커풀 점유율 | Undertow XNIO 워커 active 수 (Micrometer/JMX) |
| DB풀 점유율 | **HikariCP** `hikaricp.connections.active/idle/pending` (Micrometer 기본) |
| 지연 | `http.server.requests` 응답시간 (Micrometer/APM) |
| 부하(RPS) | 요청 카운트의 초당 증가율 |

학습 때는 시뮬레이터가 이 값들을 계산해 주고, 운영 때는 모니터링에서 읽어 정책에 넣는다 → **가상 학습 ↔ 실제 배포의 연결고리**.

## 19. 핵심 용어 정리

- **W (워커)**: Undertow 워커 스레드 수. 요청을 처리하는 블로킹 스레드.
- **D (DB풀)**: HikariCP DB 커넥션 수.
- **체류시간(mean_s)**: 요청 1건이 워커를 점유하는 평균 시간(CPU+DB).
- **db_frac**: 체류시간 중 DB 단계 비중(은닉 변수).
- **정책(policy)**: 상태→행동 매핑(학습되는 모델 = 신경망).
- **Oracle**: 미래·은닉 정보를 쓰는 이론적 상한(배포 불가, 기준선).
- **부분관측(POMDP)**: 일부 핵심 변수(요청 믹스)가 직접 관측되지 않는 상황.
- **sim-to-real**: 시뮬레이터 학습 정책을 실제로 옮길 때의 격차.
