# 강화학습 기반 포털 WAS 자원(워커 스레드 + DB 커넥션풀) 동시 튜닝

실제 포털 사양(`AP_DB자원설정`)을 반영해, 단일 WAS 노드에서 **Undertow 워커
스레드 수(W)와 HikariCP DB 커넥션풀 크기(D)를 동시에** 부하·요청 믹스 변화에
맞춰 강화학습으로 조절한다. **현재 운영 중인 정적 설정**(연구 2048워커/150DB 등)을
핵심 베이스라인으로 두고 DQN · PPO · SAC와 비교한다.

> 인프라가 고정·단일 서버·비공유라 스케일링이 불가능하다. 대신 고정 자원을 가장
> 잘 쓰는 두 소프트웨어 노브(워커풀·DB풀)를 동시에 최적화한다.

## 실제 사양 (노드 1대 기준, 엑셀 반영)

| 포털 | 노드 | 노드당 | Heap | 현재 워커 | 현재 DB풀 | 동접 | 비고 |
|------|------|--------|------|----------:|----------:|------|------|
| 연구 | 4 | 256c/512GB | 256GB | **2048** | 150 | 1000 | 장시간 DB 요청 多 |
| 사용자 | 2 | 16c/64GB | 31GB | 256(기본) | 100 | 5000 | 16코어→CPU 병목 |
| 관리 | 2 | 32c/128GB | 31GB | 512(기본) | 50 | 200 | 여유 |

(공유 통합DB: Postgres 32c/256GB×2, max 1500 — DB풀을 무작정 키우면 공유 DB 과부하.)

## 왜 이 문제가 RL에 잘 맞나 — 두 자원의 결합 병목

요청 생애주기: **워커 스레드를 전체 체류시간 점유 + DB 단계에서 DB 커넥션 점유.**

```
처리능력 = min( CPU한계 C/CPU시간,  워커한계 W/체류시간,  DB한계 D/DB시간 )
                                   ↑ 셋 중 가장 작은 게 병목
```

- 워커만 늘리고 **DB풀이 작으면** → 워커가 DB 커넥션 대기로 묶여 소용없음
- DB풀을 무작정 키우면 → **공유 DB 과부하**로 DB가 느려짐
- 요청 믹스(체류시간·DB비중)는 **직접 관측 불가** → 워커풀/DB풀 점유율·지연으로
  추론(부분관측). 부드러운 주기를 **미리 읽어 선제 조절**해야 함(예측).

## 문제를 MDP로 정의

| 요소 | 정의 |
|------|------|
| **State** (10차원, 관측 가능 메트릭) | [정규화 도착률, 도착률 추세, CPU 이용률, **워커풀 점유율**, **DB풀 점유율**, 정규화 지연, 지연 추세, W/maxW, D/maxD, 직전 드롭율] |
| **Action** | (이산) `Discrete(25)` = ΔW 5단계 × ΔD 5단계 (DQN/PPO)<br>(연속) `Box(−1,1,(2,))` → [ΔW, ΔD] (SAC) |
| **Reward** | `−sla_w·max(0,지연−임계) − drop·drop_pen − mem_cost·W − db_cost·D − thrash` |
| **Episode** | 200 제어 스텝. 한 스텝 = 워커풀·DB풀 동시 재조정 |

워커풀/DB풀 점유율을 상태에 넣어, 에이전트가 **어느 자원이 병목인지 진단**해 그쪽을
키우도록 했다(실제 Undertow·Hikari 메트릭에 대응).

## 검증된 결과 — 현재 설정이 모든 포털에서 비최적 (10 에피소드 평균)

선행 최적(Oracle, 상한 참조)을 현재 운영 설정과 비교:

| 포털 | 현재 설정 | 현재 보상 | Oracle (W/D) | Oracle 보상 | 개선 |
|------|-----------|----------:|--------------|------------:|------|
| 연구 | 2048W / 150D | −589 | **328W / 143D** | −399 | **+190** (워커 84%↓, 메모리 절감) |
| 사용자 | 256W / 100D | −1357 | **40W / 20D** | −642 | **+715** (과다 자원 정리) |
| 관리 | 512W / 50D | −270 | **37W / 9D** | −11 | **+259** (거의 SLA 충족) |

핵심 인사이트(발표 논리):

1. **현재 정적 설정이 양방향으로 틀려 있다.** 워커는 거의 항상 과다(특히 관리
   512→37, 연구 2048→328 → 메모리 대량 낭비), 반대로 DB-heavy 장시간 요청
   구간에선 DB풀이 부족해 지연↑. 단일 고정값으로는 이동하는 최적을 못 따라간다.
2. **두 자원을 같이 봐야 한다.** 워커만 늘려도 DB풀이 병목이면 소용없다 — RL은
   점유율을 보고 병목 자원을 골라 조절한다.
3. **사용자포털은 16코어라 피크에서 CPU 병목** — 풀 튜닝만으론 SLA를 다 못 지킨다
   (Oracle도 위반 존재). 이는 "코어/노드 증설이 필요하다"는 별도의 운영 인사이트로,
   정직하게 한계점에 기술한다.

Oracle은 미래를 아는 상한 참조이고, **RL의 목표는 부분관측 메트릭에서 이 선제·동시
조절을 학습**해 현재 설정·반응형(HillClimb)을 이기는 것이다.

## 프로젝트 구조

```
portal-pool-tuning/
├── envs/portal_env.py   # 2자원 결합 시뮬레이터(워커+DB, 부분관측)
├── baselines.py         # Static-Current(현재설정)/Static-Max/Static-Low/HillClimb/Oracle
├── config.py            # 3개 포털 실사양 프리셋(연구/사용자/관리)

├── evaluate.py          # 비교표·막대그래프 + W·D vs 부하 시계열(현재설정 점선 대비)
├── requirements.txt
├── models/  results/    # 실행 후 생성
```

## 실행법

```bash
pip install -r requirements.txt
python train.py --portal research --algo all --timesteps 250000
python evaluate.py --portal research --episodes 20
#  사용자/관리 포털도 동일:  --portal user / --portal admin
```

생성물: `results/comparison_<portal>.csv/png`(보상·SLA·워커수·DB커넥션수 비교),
`results/timeseries_<portal>.png`(RL이 부하에 따라 W·D를 조절하는 추이 + **현재 설정
점선**과의 대비).

## 발표(PPT) 구성 매핑

1. **적용 문제** — 실제 3포털 WAS의 워커풀·DB풀 동시 튜닝. 고정·단일 서버라
   스케일링 불가 → 자원 노브 최적화. 현재 정적 설정의 비효율 제시.
2. **모델: state/action** — 위 MDP + 결합 병목(CPU/워커/DB) 큐 모델.
3. **방법/알고리즘** — DQN/PPO/SAC. 이산 25행동 vs 연속 2D 행동. 부분관측 처리.
4. **소스 설명** — `perf()`(3중 병목+공유 DB 과부하), 점유율 상태, SB3 학습.
5. **결과/분석** — `comparison_*.png`로 RL이 **현재 운영 설정(2048/150 등) 대비**
   메모리·SLA를 얼마나 개선했는지(포털별), 오라클 상한 근접도, DQN/PPO/SAC 비교.
   `timeseries_*.png`로 부하 따라 W·D 동시 조절 거동.
6. **기여도/향후** — 실사양 기반 2자원 학습형 튜닝. 사용자포털 CPU 병목→증설 권고.
   향후: 실측(APM/부하테스트)으로 시뮬레이터 보정, 공유 DB 멀티포털 동시 최적화,
   런타임 반영(또는 권고형 어드바이저), 3개 포털 정책 통합.
